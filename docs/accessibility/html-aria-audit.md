# HTML / ARIA standards audit

This document is the normative record for praxis-kit's accessibility contract layer. For every rule
and data table the engine enforces, it names:

- the **normative source** (or states that the rule is deliberate praxis-kit policy),
- the **rule** as praxis-kit applies it,
- **praxis-kit's interpretation** — how the spec text was turned into code, and any narrowing or
  widening,
- the **test** that pins the behaviour,
- any **deliberate deviation** from the specification, with rationale.

It exists so the contract layer can be defended as an authoritative validation system rather than a
heuristic approximation, and so a reviewer can check any single rule without re-deriving it from the
specs.

## Scope

Covers the ARIA/HTML-semantics rules in:

- `lib/primitive/src/constants/aria/` — role vocabulary, implicit-role tables, role→attribute
  support.
- `lib/primitive/src/guards/aria/` — conditional implicit-role resolvers.
- `lib/contract/src/aria/` — `AriaPolicyEngine` and its rule pipeline, required-property /
  name-required / live-region data.
- `packages/core/src/html/` — per-element allowed-role tables (`role-restrictions.ts`,
  `spec/roles/*`), the input/anchor/landmark rule sets, and the HTML content-model contracts.

Not in scope here: the children/nesting content-model contracts (`contracts/html/*`), which are HTML
Living Standard rather than ARIA and are covered by their own tests.

## Conventions used across the data tables

1. **Allowed-role lists exclude the element's own implicit role.** That an explicit `role` equal to
   the implicit role is redundant is handled separately by `#checkRedundantRole` (and
   `landmarkRoleRule` for landmarks), which warns and strips it. So `<nav>`'s allowed list does not
   contain `navigation`.
2. **"Allowed but NOT RECOMMENDED" roles that are genuinely different from the implicit role are
   included.** praxis-kit validates _conformance_, not style — `<button role="link">` is
   conformant-but-discouraged HTML, so it is permitted (not flagged by `roleNotPermittedRule`). Only
   roles the spec actually forbids are flagged.
3. **`undefined` in an allowed-role table means "not modelled".** The element's permitted set is
   context-dependent in a way a single-element `(tag, props)` view cannot resolve (e.g. `<td>`
   depends on the ancestor table's role). `roleNotPermittedRule` no-ops rather than guessing. `[]`
   means the opposite: no explicit role is permitted at all.
4. **Conditional implicit roles live in resolver functions, not the static record.** `<input>`,
   `<select>`, `<img>`, `<section>`, `<form>` need more than the tag name; each has a
   `get…ImplicitRole` helper. Only tag-only roles belong in `IMPLICIT_ROLE_RECORD`.

### Role → attribute support (`ROLE_RESTRICTED_ATTRIBUTES`) — **F5 closed**

`lib/primitive/src/constants/aria/role-restricted-attributes.ts`. Now kept in lockstep with
`aria-support.generated.json` (derived from `aria-query` by `scripts/generate-aria-support.ts` — run
`pnpm aria:regen`), pinned by `role-restricted-attributes.spec-conformance.test.ts` and
`lib/contract/src/aria/spec/roles/spec-conformance.test.ts`. Any drift after an `aria-query` bump
fails those tests with the exact diff.

The realignment fixed real **false positives** — praxis was stripping valid attributes:

| Attribute                                                                                | Was missing these supporting roles                                                                  |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `aria-required`                                                                          | `checkbox`, `columnheader`, `menuitemcheckbox`, `menuitemradio`, `rowheader`, `searchbox`, `switch` |
| `aria-readonly`                                                                          | same set plus `columnheader`                                                                        |
| `aria-expanded`                                                                          | `application`, `checkbox`, `columnheader`, `link`, `switch`                                         |
| `aria-haspopup`                                                                          | `application`, `columnheader`, `link`, `rowheader`, `searchbox`, `slider`, `textbox`                |
| `aria-invalid`                                                                           | not modelled at all (accepted everywhere)                                                           |
| `aria-activedescendant`, `aria-level`, `aria-multiline`, `aria-posinset`, `aria-setsize` | one or two roles each                                                                               |

Two over-claims removed: `aria-haspopup` on `listbox`, `aria-readonly` on `tree`.

Deliberate omissions: `aria-dropeffect` / `aria-grabbed` (deprecated since ARIA 1.1). One documented
stricter case: `spinbutton` requires `aria-valuenow` (WAI-ARIA 1.2 spec text; `aria-query` 5.3.2 has
it empty) — allowlisted in the contract-side conformance test.

Earlier F5 corrections (now folded into the above): `aria-checked` +`menuitemradio`,
`aria-orientation` abstract `select` → concrete subclasses, `aria-description` added to
`GLOBAL_ARIA_ATTRIBUTES`, Name-Prohibited roles (`NAME_PROHIBITED_ROLES` +
`#checkNameProhibitedRoles`, WAI-ARIA 1.2 §5.2.8.6).

## Deliberate deviations from the specification

| ID               | Rule                                     | Deviation                                                                                                                                                                                       | Rationale                                                                                                                                                                                                                                                  | Revisit when                                                                               |
| ---------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **D1**           | `landmarkRoleRule`                       | Flags _any_ explicit `role` on `<main>/<nav>/<aside>/<header>/<footer>` that differs from the implicit role, even spec-permitted ones.                                                          | Overriding a landmark's role silently drops it from the screen-reader landmark menu; the APG never puts those roles on a landmark element.                                                                                                                 | Owner decides `error` vs `warning` severity.                                               |
| **D2**           | `ALLOWED_ROLES.li`                       | Permits `menuitem*`, `option`, `radio`, `separator`, `tab`, `treeitem`, `none`, `presentation` — wider than current ARIA in HTML ("no role other than `listitem`").                             | The APG tree/menu/menubar/tablist patterns build directly on `<li role="…">`. Enforcing the spec text would flag the framework's own reference patterns.                                                                                                   | ARIA in HTML restores an explicit list, or the APG examples change.                        |
| **D3**           | `#checkStandaloneRegion`                 | Warns on `<article role="region">` even though the allowed-role table lists `region` for `article`.                                                                                             | `region` is a weaker generic landmark; `<article>` already has richer semantics — this is almost always a mistake. Advisory only.                                                                                                                          | —                                                                                          |
| **F4 (partial)** | `#checkRequiredAriaProperties`           | `<input type=range/number>` still warns for a missing `aria-valuenow` on the _implicit_ `slider`/`spinbutton` role.                                                                             | Existing tested behaviour; the value is arguably worth authoring for SSR snapshots. `<select>` is exempted because its expanded state is not authorable at all.                                                                                            | Owner decides whether native implicit roles should _never_ get required-property warnings. |
| **D4**           | `IMPLICIT_ROLE_RECORD` `header`/`footer` | `<header>`/`<footer>` are always mapped to `banner`/`contentinfo`. The spec scopes those to _top-level_ elements — nested inside `<article>/<section>/<aside>/<main>/<nav>` they are `generic`. | `AriaContext` is a single-element view with no ancestor chain; distinguishing top-level from nested needs tree context this layer deliberately does not carry. Nested `<header>`/`<footer>` are uncommon and the failure mode (an extra landmark) is mild. | `AriaContext` gains ancestry (an architecture decision, tracked as **F8**).                |
